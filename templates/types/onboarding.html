01

The working model

8 min

Northwind Ingestion is an internal acceptance and landing path. Producers send events to the gateway; one shared queue buffers them; consumers validate and write them to the warehouse.

Carry this sentence: the current queue is both the buffer and the failure boundary for every first-party producer.

The diagram also shows the proposed dispatcher and split queues. Those components are not production facts yet; they belong to RFC 014.

02

Four boundaries that prevent wrong assumptions

12 min

Acceptance

202 is queued, not warehoused

Lookup and freshness are later concerns. Do not promise downstream visibility at gateway acceptance time.

Identity

Event ID is the retry anchor

Reuse it. A new ID turns a retry into a second logical event.

Ordering

Producer-local order is not guaranteed

The proposed split does not remove a promise because that promise does not exist today.

Rollback

Queues are retained, never deleted

Cutovers flip traffic. Destructive queue actions are not a rollback strategy.

If a design or incident response crosses one of these boundaries, stop and open the owning contract or runbook before acting.

04

Run one event locally

15 min

  1. Run the tests

    bashmake ingest-test

    Success: contract and consumer tests pass.

  2. Start the gateway

    bashmake ingest-run

    Success: the log contains listening on 8443.

  3. Post the synthetic event

    bashcurl -k https://127.0.0.1:8443/events \
  -d '{"id":"evt_learn","type":"onboarding.ping"}'

    Success: 202 repeats evt_learn.

05

Prove readiness with understanding, not task completion

8 min
  • Draw the current path and mark its single failure boundary.
  • Explain why scaling consumers recovers an incident but does not remove recurrence.
  • Name the current and proposed overload responses without mixing them.
  • Locate the runbook, API source, RFC, ADR, dashboard, and latest postmortem.
  • Ask who can approve shed behavior and where the chaos environment will live.

You are ready for the next document when: you can explain what is current, proposed, unresolved, and safe to change without relying on memory or access to production.
