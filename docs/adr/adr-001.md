# Keep reading structure and visual voice as two independent axes

**Type:** Architecture decision record · ADR 001
**Status:** Accepted
**Date:** 2026-11-13
**Supersedes:** none

## Context

A document has two separable properties. How it is read (where the answer sits,
which relationships are visible, which modules repeat) depends on the reader's
question. How it looks (paper, ink, accent, type, borders) depends on the
audience and brand. Early documents tied the two together, so a new voice meant
rewriting structure and a new structure meant restyling.

The repository ships 34 types across 11 reading patterns and six theme files.
One body already renders under two themes (`proposal-horizon`, `proposal-coral`).

## Decision

We will declare the two axes separately on the root element, `data-pattern` for
structure and `data-theme` for voice. A theme change must not alter information
architecture, and a pattern change must not invent facts or change the evidence
state. Pattern CSS contains no colour literals.

## Consequences

Benefits:

- Any type can be shown in any theme, which the proposal examples prove.
- A client brand is one new theme file, not a fork of every document.
- Each axis has its own check: the validator audits themes, the catalog audits
  patterns and modules.

Costs:

- A theme cannot reshape a document, so every difference in voice must be
  expressible as token values (see ADR 002).
- A pattern cannot restyle itself, so visual identity per pattern has to come
  from structure and not from colour.
- Contributors must decide which axis a change belongs to before editing.
