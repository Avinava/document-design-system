# Spread default themes across types

**Type:** Architecture decision record · ADR 004
**Status:** Accepted
**Date:** 2026-11-13
**Supersedes:** none

## Context

The `default-theme` field in each type's yaml block currently resolves to four
themes: `field-notes` for 12 types, `executive-navy` for 8, `console-violet` for
8 and `editorial-coral` for 6. The first, second and fourth are light themes with
similar scale and density, so 26 of 34 types open in a similar light voice.
`horizon` and `brand-template` are the default for none.

A default is the only voice most readers ever see. When most defaults look alike,
the theme axis (ADR 001) exists in the contract but not in the product.

## Decision

We will choose each type's default theme for its reader and register, and keep
the defaults spread so no single theme dominates the catalog. The default is set
only in the type's yaml block (or in `catalog.COMPOSED` for a composed example),
never in a second copy. New themes are added to give the spread somewhere to go,
and the voice check in `scripts/audit_theme.py` will treat two indistinguishable
themes as an error.

## Consequences

Benefits:

- The first screens of different types differ in voice as well as structure.
- The default for a type is a documented choice with one place to change it.

Costs:

- Changing defaults regenerates `examples/`, the gallery and screenshots.
- Each new theme carries a font, a print block and a contrast audit to maintain.
- A reader who preferred the old default must override the theme by name.
